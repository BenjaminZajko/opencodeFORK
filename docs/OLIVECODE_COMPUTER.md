# Computer mode — browser and macOS desktop preview

Choose **Computer** beside Assist, or type `/computer`, then choose **Start Computer mode**. Describe your task. On macOS this single mode can use both websites and native apps; OliveCode chooses the relevant tool, and can use both within one task. On Windows and Linux it currently controls websites only. OliveCode asks before opening its own visible browser, clicking, typing, replacing text, navigating, opening/switching tabs, capturing a screenshot, or going back. Read the action and choose Allow once, Allow always, or Reject. Allow always enables browser actions in this chat until OliveCode restarts (or the project instance is disposed), including clicks that can submit forms or change site data. Other chats do not inherit this permission. Screenshot capture still asks separately. **Stop** closes that browser and cancels the current task; `/computer` also offers Stop and return to coding. Closing the browser window stops its browser tools.

For a first test: “Open https://example.com and tell me the heading and what its link does. Do not click the link.” Then try an ordinary search or a harmless form on your own test website.

The browser uses a fresh temporary profile, separate from personal Chrome/Edge profiles. It retains that profile within the chat until Stop, closing the window, project disposal, or 15 minutes without browser actions. Stopping removes the profile and its cookies. It never attaches to your normal browser. Keep the app running while using Computer mode.

Page text and visible controls are sent to the selected model. Enabled Assist models receive browser evidence to plan and review larger tasks. Choose a local model for local inference. Known private input values are hidden from text observations; private details, verification codes, CAPTCHAs and payment fields are handled by you in the browser. Avoid exposing confidential page content to cloud models.

## Supported in this version

- Installed Chrome, Microsoft Edge, Chromium, or an existing Chrome for Testing installation. Safari is not supported.
- Browser tabs: open, observe, navigate, click, append or replace/clear text, scroll, back, open a new tab, switch an observed tab, close the browser. Tabs belong only to OliveCode’s dedicated browser. Closing the active tab can recover another remaining tab; switching always invalidates old page targets.
- Optional screenshots, sent as image attachments only to a model whose catalog entry accepts images. Screenshot capture requires separate approval and is refused when a known private field is visible. Images can still show other confidential page content, so review the page before approving.
- Structured page observations, so text-only free models can operate supported page controls.
- Fresh target IDs and observation revisions, stale-control checks, serialized actions, timeouts, and a 120-action budget per new task. The agent also has a 60-step model limit. Assist can identify unfinished work within those bounds.
- Human approval for state-changing actions, with optional Allow always scoped to the current chat. Screenshots remain separate, one-time approvals.
- Coding tools, arbitrary JavaScript, MCP tools, automated private-field entry and file downloads are unavailable in Computer mode.

Browser mode controls its own browser input, rather than the system pointer. Desktop mode below controls macOS apps. Canvas-only controls, cross-origin frames, file pickers, uploads, select menus and native dialogs may require manual handling. It does not yet provide coordinate-based visual clicking, unattended workflows, browser installation, or guaranteed task completion. Mac browser integration is tested; Windows discovery is implemented but still needs a real Windows run.

## Implementation

The browser adapter talks directly to Chrome DevTools Protocol over a random local port, inside a dedicated profile. Application-owned observation scripts run in an isolated execution world. Models supply only supported actions, numeric control targets and observed tab IDs. Each action reobserves the page and leaves tool evidence for completion review. Browser processes and profiles are disposed with the project instance, on task interruption during an action, or explicit session cancellation. The Stop button uses the existing authenticated session abort endpoint.

Browser-driven content remains untrusted. Approvals and restricted tools reduce risk but do not prove a page's intentions. A user can override permissions in local configuration; doing so changes the approval guarantees. Modified software and local processes with access to debugging connections are outside this boundary.


## macOS desktop control

Choose `/computer` → **Start Computer mode**, then describe the Mac app task. Your cloud/local model selection is preserved. Try: “Open TextEdit, create a new document, type Hello from OliveCode, and verify the text. Leave it unsaved.” Desktop mode uses the actual pointer and keyboard in your normal apps; it does not create a private desktop. Close unrelated private windows before using it.

The first task checks macOS permissions. When Accessibility is already enabled, it continues directly to the requested app. Setup for a permission already granted returns status without reopening System Settings. If Accessibility is unavailable, enable **OliveCode Computer** (or the application macOS names in its permission prompt) in System Settings → Privacy & Security → Accessibility. The model can open that settings page but cannot enable the permission itself. Reply that you have enabled access, then retry the task. macOS 14 or newer is required. Screen Recording is optional for ordinary accessibility controls. Enable it for approved active-window screenshots or on-device screen-text reading. Text-only models can use both accessibility observations and locally recognized screen text; image-capable models can also receive the actual picture.

- Active-window observations include app, title, visible text, control targets and revisions. Models can activate an installed app by bundle identifier, click targets, append/replace text, scroll and press supported keys/modifiers. A fresh observation follows each action. App/window changes invalidate previous targets.
- Optional screenshots capture only a uniquely matched active window. They require separate one-time approval and an image-capable lead model. Coordinate clicks require that latest approved screenshot and stay within its window bounds. Known private fields and incomplete accessibility observations block capture; confidential content outside recognized fields can still be visible.
- Private input controls are excluded from observations and automated entry. Known terminal apps and System Settings are blocked for ordinary desktop actions. Setup opens only the relevant macOS privacy pane. Coding, shell, arbitrary JavaScript, browser and MCP tools are excluded from this agent. These boundaries are not an OS sandbox: the operator still uses real apps with the user's privileges.
- **Allow always** grants desktop window reading and ordinary mouse/keyboard actions only in the current chat until restart/project disposal. Browser permissions are separate; screenshots remain separate. Enabled Assist advisers receive observed desktop text for larger tasks, without getting desktop tools themselves.
- **■ Stop** cancels the task and terminates the native helper. **Control+Option+Esc** terminates desktop control from any foreground app, once Accessibility is enabled. The helper checks only this emergency chord, not typed text. Switching modes cancels the previous task first. Only one chat in this OliveCode process can own the desktop, with serialized input, a 120-action task budget, action timeouts and five-minute idle cleanup. Pending human approvals suspend idle cleanup; approval, rejection or cancellation releases that hold. Stop still immediately terminates control while an approval is pending. Separate independently launched OliveCode processes are not covered by that in-process lock; use one desktop task at a time.

Some apps expose little or incomplete accessibility information. Secure dialogs, hidden controls, changing window layouts, remote desktops and unusual custom controls can require manual handling. No unattended operation or guaranteed completion is promised. Windows native desktop input is not implemented; Windows browser mode remains available and needs native Windows testing.

The helper is compiled from `packages/opencode/src/computer/native/desktop.swift`, ad-hoc signed with a stable identifier, embedded in macOS builds, and extracted into OliveCode's data directory as `computer/OliveCode Computer.app`. Users do not need Swift, Python or a separate helper download. Builds made on non-macOS hosts do not include the macOS helper. Developer builds can compile the helper as `src/computer/native/desktop-helper` locally. Production signing/notarization and permission persistence across public releases still need release validation.

Validation for this milestone covers helper compilation, coordinate/private-field/Unicode self-tests, transport serialization/Stop/abort/race checks, tool isolation, chat-scoped approvals, the 120×30 mode selector and compiled app/helper startup. The browser workflow is exercised end to end against a real Chromium form. The user has now confirmed real TextEdit document creation and exact text entry from the permitted Terminal launch. Codex’s test context still lacks Accessibility and Screen Recording: the new capture, window-switching and focus-recovery paths, plus the global emergency chord, need physical validation from the permitted launch before Desktop mode is treated as stable.

Native API references: [Apple Accessibility trust](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions), [window screenshots](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager), [window shadow configuration](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/ignoreshadowssinglewindow).


### Desktop recovery and verification

Missing action revisions are filled from the latest observation already delivered to the model; explicit stale revisions remain rejected by the native helper. A missing typing target is filled only from an observed focused AXTextArea, never an Open-dialog search field. Observations include focused control, window role and an edited flag when the app exposes it. A failed action is visibly labeled with its error in chat details. A subsequent observation alone does not establish that the failed action succeeded.

A real Allow once/Allow always interaction can move focus to OliveCode's Terminal window. Permission receipts distinguish that user interaction from a cached automatic grant. Only after an actual prompt may Desktop mode restore its already-observed app/window from the approval terminal; normal foreground/revision/target guards still apply. Automatic grants do not restore windows over unexpected user app changes. Screenshots retain separate approval.

Short permission acknowledgements such as “I enabled it” retain the previous Desktop/Browser task for Assist and Follow-through review. Review cannot mark a task complete when its most recent input action failed; when reviewers are unavailable, a failed action still produces corrective follow-through guidance. These are evidence checks, not a guarantee that a free model will always complete a task correctly.


### Approval wait lifecycle

A reported TextEdit task waited approximately 38 minutes for tool approval after status had already reported Accessibility enabled. The previous five-minute idle cleanup stopped its helper while that approval was pending, so later actions failed. Status guidance now follows the actual permission result instead of unconditionally asking for setup. The helper stays alive while a Desktop tool awaits approval, preserving its observations; the hold is always released on approval, rejection, failure or interruption. Explicit Stop remains final for the current request and releasing a pending approval cannot revive it. Advisers distinguish stopped control from missing OS permission and must not invent a permission problem from a stopped-helper error.

Regression tests use a shortened real idle deadline to verify the helper survives a longer approval wait, idle cleanup resumes afterward, Stop stays final, and the actual tool releases its hold after both approval and rejection. Native status/self-tests and the compiled browser/helper smoke cover packaging. Physical TextEdit input still requires validation from the user's permitted OliveCode launch context.


### Reasoning-only response recovery

Some free models end a turn after reasoning about the next action, without actually calling the tool or providing an answer. OliveCode now detects this empty finish before completion review and requests continuation from the last real observation, retaining the original task and avoiding a replay of completed actions. This recovery applies even with Teamwork and Follow-through disabled, and cannot depend on an unavailable reviewer. It makes at most two continuation attempts within the existing agent step limit. If no visible answer follows, chat receives an explicit unfinished-task explanation instead of an empty result; reasoning is never promoted into an action or success claim. Cancellation and permission boundaries remain in force.

Validation includes scripted local-provider session-loop tests for recovery into a completed tool action, repeated empty responses, bounded retries and Stop during recovery. The compiled Desktop integration fixture intentionally returns a reasoning-only stop after native status and makes both completion reviewers unavailable: the operator resumes, closes its helper and returns its verified status result. No personal windows are read by this fixture. This reproduces the response failure without asserting that a real free model is guaranteed to finish the full TextEdit workflow.


### Provider rejects an invented tool name

Desktop operations are arguments to the single `desktop` tool, for example `desktop({action: "type", text: "Hello", target: 1, revision: 2})`. They are not separately offered tools named `type`, `click`, or `status`. Operator instructions and the tool description now make this explicit.

When a provider rejects a generation for calling an unoffered tool, OliveCode supplies the actual available tool names and schemas and retries at most twice. This handles HTTP400 API errors and streamed errors alike, without treating normal authentication failures, context errors or permission refusals as repairable tool-name mistakes. Nothing in the provider's rejected generation is executed. If tool activity already began in that stream, the repair is refused to avoid replaying side effects. Existing desktop approvals, stale-observation checks and Stop continue to apply.

Tests exercise the entire TextEdit sequence against a synthetic native-window service, injecting the reported HTTP and streamed rejection before valid calls. Status, app activation, document creation, exact text entry and verification run once each through the actual Desktop tool, and there is no Save action. A separate opt-in test has also passed with the real Groq GPT OSS120B model against those synthetic windows (about18.5seconds); it sent the correct tools, typed the exact text once and returned a final answer. It receives no real desktop data, and ordinary tests do not use live provider credentials. Physical macOS input remains a separate validation boundary.


### Windowless apps, concurrent actions and repetition

Dismissing TextEdit's Open dialog can leave the app active with no document window. This is now a valid observation (`windowAvailable: false`, a fresh revision and no controls), rather than a failed click. Old window targets and screenshots are cleared. Only Command+N is permitted in that state, and only for the same observed foreground app and revision. Other keys, stale references, app changes, private controls and terminal apps remain blocked. The new document must be observed before text entry.

Desktop generations request sequential tools from supported providers. The tool also independently permits only one action per assistant turn, including when a provider ignores that setting. An extra parallel action is explicitly rejected without being executed; the next turn reads the first result and observes before acting. Stop remains available even if that turn already used a desktop action.

Streaming desktop text that cycles through the same prose is stopped early, replaced with a short interruption record, and given at most two recovery attempts from actual tool evidence, independently of Assist. Old repetitive desktop turns are condensed only when constructing a new model request, preserving the stored chat and tool evidence. This prevents the reported repetition/context-overflow spiral without treating attempted actions as completed. Local recovery/UI metadata is excluded from provider option namespaces during replay.

Regression coverage includes Cancel → windowless observation → Command+N → exact text → verification, two parallel Cancel/Command+N calls, repetitive streaming, bounded recovery, old-history replay, actual outgoing Groq sequential-tool settings and Stop. Two real Groq GPT OSS120B runs against synthetic native windows passed: ordinary new-document creation and the Cancel/windowless recovery route. These real-provider tests validate model integration; they do not establish that physical macOS input has been tested from Codex's unpermitted launch context. Native helper compilation and policy self-tests cover the windowless shortcut's foreground, revision and key restrictions.


### Screen reading, window switching and input receipts

Desktop mode sees one active app window at a time, rather than a continuous video or every monitor. Accessibility observations provide text and numbered controls. `look` additionally captures that window with separate approval and runs Apple Vision text recognition locally. It provides recognized text, confidence and numbered text positions to every model. Only image-capable lead models receive the image attachment; for text-only models the raw picture stays local. Enabled Assist may receive the extracted text. This makes more interfaces usable with text-only free models, but OCR cannot interpret unlabeled icons, colors or pictures the way an image-capable model can. The Cloud picker labels catalog entries that accept images with **Images**; the Computer dialog explains the selected model’s view.

`click_text` clicks the center of a label from the latest approved `look`. Recognition can be wrong, and a text label is not necessarily a button. `click_point` remains restricted to an image-capable lead and its latest approved screenshot. Visual targets expire after sixty seconds and are invalidated by observations/input; foreground app, window identity, bounds, private fields and covered-point checks remain enforced. Neither path supports arbitrary full-screen capture or unobserved coordinates.

`find_app` searches a specific installed app name and returns up to ten matching names/bundle identifiers, excluding known blocked apps. It does not enumerate personal windows or read app content. `windows` lists the current app’s window titles and bounds. `focus` restores that already-observed app or switches to a listed window, then returns a fresh observation. After an overlapping-window refusal, the operator can focus once and retry from the new view, rather than repeating stale clicks. Typing into a control that already owns keyboard focus avoids an unnecessary pointer click. Common supported shortcuts now include editing, find/navigation, new document, window operations and page movement; this remains a fixed key whitelist, not arbitrary commands.

If a click/key/text event is sent but the user switches apps or verification fails afterward, the helper returns an **input sent, observation needed** receipt. It does not observe an unrelated app or falsely label the original action as unsent. Further input waits for a new observation or explicit focus recovery, and completion review rejects an unverified receipt until the same app is successfully observed. The operator must inspect what happened before repeating input, avoiding duplicate text or repeated side effects.

Validation uses real Apple Vision on a generated image containing “Hello from OliveCode,” native app-name discovery, coordinate/expiry/privacy/Unicode policy tests, and synthetic windows through the full operator/tool/session loop. A real free Groq GPT OSS120B run successfully used `look` and `click_text`, typed the exact text once and verified it against synthetic native windows, without receiving an image (about thirty-five seconds). These checks validate model integration and local recognition; they are not a physical screenshot or mouse test. The user’s confirmed TextEdit run establishes the earlier physical typing path, not every new capability.

Try from a fresh Computer chat: “Open TextEdit, use screen-text reading to find New Document if its picker is open, create a new document, type exactly Hello from OliveCode, verify the text, and leave it unsaved.” Screen-text reading will ask for capture approval and requires macOS Screen Recording. Ordinary TextEdit accessibility control still works without that extra permission.


### One Computer mode

The chooser now has one Start entry and Stop/return to coding. On macOS the Computer agent receives browser and desktop tools together, with separate browser/desktop permission scopes and separately approved captures. Websites normally use the dedicated browser’s structured page controls, which do not move the system cursor. Native app work uses the actual system cursor and keyboard. Combining their entry point does not change how those underlying tools operate, attach to personal browsing, or grant shell/file/MCP access.

Each assistant turn may execute only one computer action across both tools; an extra action is refused before approval or input. Close remains available. Model requests also disable parallel tool calls. Browser and desktop targets/revisions remain separate; the operator must explicitly activate/focus and observe the intended app before desktop input after browser work. The shared Stop button aborts the task and closes both adapters. Old Desktop-agent chats remain supported, but new tasks use the unified Computer entry.

A useful combined test: “Open example.com in your browser, read its heading, then create a new TextEdit document containing only that heading. Verify the document text and leave it unsaved.” This needs macOS Accessibility for TextEdit. Screenshot/recognition permission is only needed if the task actually captures a window. No native Windows desktop input is added by the unified button.


### Mouse gestures and observed menus

The macOS adapter now supports deliberate pointer movement to an observed control (`move`), single left/right clicks, left double-clicks (`click` with count2) and short left-button drags between two observed controls (`drag` with target/toTarget). Right-click and double-click also apply to approved image/text click targets. Pointer positions are returned relative to the active window when the pointer is inside it; moving is distinct from clicking. Context menus exposed through Accessibility are included as fresh controls for the active app, including their observed bounds. A menu outside its parent window can be selected only from those observed menu targets; screenshot coordinate clicks remain inside the captured window.

Drag is currently restricted to the same window, between control centers. Both controls must be enabled and non-private, their references current, the sampled straight-route points checked on connected displays, and the foreground/window stable. Dragging does not provide arbitrary-coordinate or cross-window drops, window resizing or drag-and-drop uploads. Pointer movement separately accepts positions inside the observed window. Rows/cells/images can be observed targets, but an app may not support dragging or clicking a particular target. The model must verify the actual result, not treat delivered events as proof of a successful drop.

Approvals show the actual mouse gesture, source and destination. New mouse actions share existing chat-scoped permissions and the one-action-per-turn guard. Private controls under the pointer are checked, including coordinate clicks. The native helper releases held left/right mouse buttons on gesture completion, errors, normal exit, SIGTERM/SIGINT and the emergency chord. A release is posted at the latest drag point; it cannot undo a drop or earlier input. Once stop handling begins the latch refuses further mouse events.

Validation includes actual CGEvent construction/click-state tests, bounded/nonfinite/identical-point route checks, fake-sink button release/no-input-after-Stop tests and a real helper-process SIGTERM test using a fake event sink (no physical input). Tool tests verify exact gesture fields, drag destination disclosure, approval rejection without native calls, disabled/stale/missing references and failed-drag completion evidence. Ten terminal UI tests cover mouse approval labels plus the unified mode and Stop. Physical mouse gestures and menu observations still require testing from the permitted Terminal launch; the user has confirmed the earlier real combined website-to-TextEdit task.

### Fresh-request focus and window-relative movement

A follow-up request to move around the screen reused revision6/target1 from a completed TextEdit request while Terminal was foreground. Native task state resets between human requests, so those controls were historical. The operator then retried clicks/observations and an activation that never brought TextEdit forward; Accessibility was already true. Desktop tools now use only observations after the latest real human request. Old references fail before approval/input and instruct activation of the intended app; synthetic recovery messages do not reset this scope.

Explicit activation now reuses an existing app process without reopening its document picker, requests app activation and, if the approved Accessibility attribute is settable, asks the requested app to become frontmost. It waits up to two seconds for foreground PID confirmation, without reading unrelated app content. The same foreground check supports explicit focus and restoration after a real approval. This is not hidden restoration on cached grants and does not bypass macOS permissions. If the request is not honored, no mouse/keyboard input is sent and the operator asks for manual foregrounding. Apple documents activation as a request rather than guaranteed focus: https://developer.apple.com/documentation/appkit/nsapplication/activate%28%29?language=swift

`move` now accepts either an observed target or explicit finite nonnegative x/y from the latest observed window’s top-left, never both. Native checks keep the point inside that current window/on connected displays, in the intended foreground app and outside recognized private controls. Movement sends no click, so explicit window positions can be used by text-only models without screenshot capture. This does not enable arbitrary whole-screen movement or coordinate clicks without their existing visual requirements. Approval discloses the requested position, and observations return actual window-relative cursor position when inside. Tests cover ambiguous/partial/nonfinite coordinates and old-request references with no native call; native self-tests cover delayed activation confirmation and bounded failure. Physical activation fallback still requires validation from the permitted Terminal launch.


### Consistent coordinates, pointer-only constraints and bounded history

The three-position user run confirmed actual cursor coordinates (192,197), (475,378), (400,200). It also exposed three bugs: native control/window bounds were global while cursor/move coordinates were relative; the windowless instruction prompted unrequested Command+N; and completion checks retried beyond the requested outcomes before compaction failed.

Active-window `bounds`, control/menu bounds and cursor positions now share the window-relative screen-point coordinate system. The window starts at (0,0); x must be less than its width, y less than its height. Internal screen hit testing is unchanged. Invalid coordinate moves fail before approval/native input with the dimensions and unchanged revision. Window-list entries still describe screen placement; select those windows by their observed index and use the fresh focused observation for movement.

For explicit pointer movement requests saying without clicking or changing text, the tool refuses keyboard input, document creation, clicks, typing, filling and drags before approval/native input. A windowless app must find/focus an existing window or request user help. Other tasks that request a new document remain supported. The completion guard recognizes the requested number of distinct actual cursor results in the same unchanged document and does not treat an unnecessary failed extra move as invalidating them. Duplicate coordinates, changed text/window, mismatched cursor coordinates, unverified receipts and successful forbidden input do not qualify. Review instructions require stopping at the original scope.

Model replay retains only the latest current-request actionable desktop/browser view and its image. Older observations retain bounded text, actual cursor evidence and verification flags; controls/images are removed from replay. Original chat details are unchanged. The compaction serializer and advisers also receive compact evidence; computer reasoning prose is excluded from summaries because it is not executed-action evidence. This reduces context growth; it does not guarantee arbitrary tasks can never exhaust model limits.

### Visible control and Background browser

The Computer chooser now offers Start visible control (websites plus supported Mac apps) and Start background browser (websites only), followed by Stop/return to coding. Both retain progress in chat and Stop. Background is a separate headless Chromium profile, not a hidden Mac app or a second macOS Space. Switching execution mode replaces the browser rather than silently continuing in the wrong mode. Reopening after Stop creates a fresh browser. Private-field/login/CAPTCHA handling requires Visible control and restarting the relevant task; the headless profile is not promoted into a visible window.

The background agent has browser/question/todowrite only. Native desktop, shell/files, MCP and resource tools are excluded from both tool registry and runtime augmentation. Browser service requires the selected execution mode; observations from the other mode cannot be used. The same action approval, screenshot approval, revision/owned-tab/privacy checks and Stop apply. The background browser never posts system cursor or keyboard events. Chat observations and, for image-capable models, separately approved screenshots provide progress checks. There is no live background screen streaming or preview button in this version.

Visible native pointer moves use a bounded smoothstep path at approximately 60 samples per second, with about 0.2–0.55 seconds travel according to distance. Clicks move along the same path before button events; drags ease their route and approach the source smoothly. Every motion checks foreground/window stability, Stop/cancellation and the actual pointer against the previous event. Manual pointer displacement stops motion without starting a click; interrupted drags release the button. It cannot undo already sent input. Transit outside the destination window moves only and does not inspect other windows; private/obstruction guards apply inside the observed window and at the destination. User switching apps likewise invalidates motion.

True concurrent native app operation requires an isolated desktop session/VM or remote computer, not another Space in the current session. That backend is not implemented here. Quartz events enter the window server/session stream: https://developer.apple.com/documentation/coregraphics/cgeventtaplocation/cgsessioneventtap . Do not describe background browser as background TextEdit/full desktop control.

Validation: backend and TUI typechecks; Computer chooser tests (including 60x20 and background Stop); registry/tool/session/browser regressions; actual headless service page observation, wrong-mode refusal and Stop; native helper self-test for eased endpoints, monotonic path, acceleration and invalid input. Compiled fullapp smoke in background mode verifies isolated real Chromium form/tabs/fill/approved image attachment/Assist/Stop with local scripted models. Native status/Stop smoke reads no personal windows; actual animation/human interruption remains a Terminal-launch user test. Reopen the launcher, choose Visible control, then repeat the three-position test with an existing TextEdit window. ### Short typing and Background Mac connection preview

Short native typing now emits one complete grapheme per step for requests of up to 80 characters, with roughly 20–65 ms delays depending on spaces/punctuation. Larger requests retain the original fast 32-UTF-16-unit chunks, preserving surrogate pairs. Every step checks focus, window/revision, cancellation and Stop; typing does not continue into a different field. No delay is added to browser form filling. The user has confirmed the earlier actual visible pointer animation; real delayed typing still needs a visible-launch test.

Computer now includes Start background Mac for an explicitly user-configured isolated Mac/VM. Its browser runs headlessly; native actions use a fixed helper command over a trusted SSH alias from OLIVECODE_BACKGROUND_MAC_SSH. Native transport performs an internal identity handshake before forwarding app actions, rejects the host identity/missing identity, and serializes ownership by guest identity across aliases. Identity hashes are not part of model messages. Strict SSH host-key checking, batch authentication and disabled agent forwarding remain mandatory. User configuration supplies the target; models cannot supply shell commands/credentials/SSH parameters. There is no host-control fallback. Native screenshot/Accessibility approvals remain unchanged and apply to the guest.

The portable package now contains a Background Mac folder with a signed guest helper app, install script and SETUP.md. The install script is run manually inside the guest and does not set permissions, enable SSH or install a VM. A logged-in guest and its app permissions are needed; macOS TCC behavior under SSH remains unverified until a real-guest test. See OLIVECODE_BACKGROUND_MAC.md for precise setup and remaining work. A managed one-click VM installer/lifecycle and live VM viewer are not implemented. Background Mac is a connection preview, not a claim that native background work is ready on this host.

Stop now closes input and requests SIGTERM, giving the helper its mouse-button release handler time to run, with a bounded one-second forced-kill fallback. A process fixture verifies the release handler runs; network disconnect and actual guest mouse release still require integration testing. Native self-tests verify short/long boundaries, emoji and combining accents, lossless UTF-16 reconstruction, and the earlier eased mouse path checks. Backend/TUI typechecks, chooser tests, isolation/ownership/Stop fixtures and existing Computer regressions pass. Build 0.0.0-olivecode-dev-202610071946 includes these changes.
