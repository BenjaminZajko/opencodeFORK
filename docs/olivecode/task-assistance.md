# Task assistance

Teamwork and Follow-through are on by default for substantial Build requests. Open **Assist** beside Cloud and Local, or type `/assist`, to switch either one off. Short acknowledgements and simple questions skip the extra calls. These settings are saved in the current project.

Teamwork uses the selected model as the lead. Up to two other eligible free models advise it without running tools or editing files. The first sees a bounded, ignore-aware list of project file names and proposes a plan with concrete deliverables, an idea of what "done" means, and proportionate verification. The second checks that proposal against the request and challenges omissions. For longer tasks, a teammate checks actual progress against the requested outcome after five completed or failed tool calls, with at most two such checkpoints. As new evidence appears, the initial plan stops being repeated to the lead. Local tasks use installed Ollama models only; cloud tasks use active free cloud providers. OliveCode prefers different providers for distinct perspectives and skips known cooling models.

Follow-through reviews each requested outcome against the tool outcomes and the lead's answer. On tasks with at least four tool outcomes, two independent eligible models perform the first completion check. A grounded concern sends the lead back to work; later rounds use one reviewer. A genuine blocker should identify the exact input or external condition needed. The process stops when the request appears complete, needs the user's input, repeats a gap without any new tool work, reaches the model's step limit, or reaches six review rounds. A reviewer has no independent filesystem access, so it cannot certify correctness. Failed adviser requests do not fail the lead task.

The previous implementation had no project map, no mid-task check, and only one reviewer at a time. It also looked only in stored sign-ins for peers, which excluded providers configured through keys or environment settings. A localhost simulation caught that bug and now verifies plan exchange, a reviewer-requested continuation, five real file reads triggering a progress check, and two distinct first reviewers. The compiled app and terminal UI type checks pass. Real provider quotas and improvement in task outcomes still need a larger set of human and repeatable evaluations.

Design choices follow the evidence that independent, bounded agents help most when they bring distinct perspectives and actual observations, while coding work is less parallel than broad research. See [Anthropic's multi-agent engineering account](https://www.anthropic.com/engineering/multi-agent-research-system), the [Reflexion paper](https://arxiv.org/abs/2303.11366) on using task feedback to guide subsequent attempts, and [OpenAI's guidance on trace-based agent evaluation](https://developers.openai.com/api/docs/guides/agent-evals).
